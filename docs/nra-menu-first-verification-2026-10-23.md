# Перевірка збору від меню до статей

23 жовтня 2026. Доповнення до попереднього аудиту; попередній звіт залишено без змін.

**Уточнена задача:** відтворити доступні клієнту списки статей під обраними пунктами меню, зберігати шлях переходу, один раз завантажувати кожну унікальну статтю та додавати всі наступні знайдені шляхи. Глибину пагінації визначає звичайний інтерфейс сайту. Не розширювати збір через sitemap, it=100 або приховані архіви.

**Висновок: так, цей підхід здійсненний і відповідає уточненій задачі.** Для такого результату не потрібно відновлювати breadcrumbs із URL або внутрішніх тегів статті.

## Реальна перевірка браузером

1. На головній American Rifleman відкрито Open the menu. Видно групу Sections із Armed Citizen, Columns, Historical, News, Reviews, Tips & Techniques, Videos.
2. Натиснуто Armed Citizen. Перехід на https://www.americanrifleman.org/armed-citizen/. На сторінці є власний список Latest Stories і Page 1 of 50.
3. Натиснуто звичайний Next. Перехід на https://www.americanrifleman.org/armed-citizen/?pg=2&it=10&st=True&sd=Descending&cnt=All&cat=1688&f=latest. Список змінився, індикатор — Page 2 of 50.
4. З другої сторінки відкрито статтю https://www.americanrifleman.org/content/the-armed-citizen-sept-21-2026/. Її URL не містить шлях Armed Citizen, але crawler уже знає його з контексту списку.
5. Відкрито верхнє меню Reviews, натиснуто Guns, потім картку Taurus зі списку Latest Stories. Отримано https://www.americanrifleman.org/content/rifleman-review-taurus-raging-hunter-in-350-legend/.
6. Відкрито Reviews → Gear, у Latest Stories знайдено ту саму картку. Перехід дав точно такий самий URL Taurus.

Це перевірка репрезентативних переходів, а не повний crawl усіх 50 сторінок чи всіх доменів. Постійне сховище, дедуплікацію та завантаження медіа в цьому браузерному досліді не реалізовували.

## Що означають отримані зв’язки

Можна достовірно сказати: сайт показав Taurus у списках під Reviews → Guns та Reviews → Gear під час перевірки. Для відтворення видимої навігації цього достатньо. Це не вимагає стверджувати, що внутрішня редакційна категорія Taurus — Gear.

Спільність списків між підрозділами не блокує запропонований метод. Вона означає, що результат матиме спільні статті під кількома шляхами, як і показує сайт. Зв’язок варто назвати navigation membership або місцем показу, відокремивши від власних тегів статті.

Потрібно збирати визначені блоки розділу: основний список та обраний featured. Не брати автоматично всі посилання сторінки: Most Popular, реклама, глобальні рекомендації, меню й footer мають іншу роль. Якщо клієнту потрібні також ці блоки, зберігати їх як окремі типи показу, а не змішувати з основним списком.

Sections — групувальний заголовок меню, а не обов’язково сторінка. Його можна зберегти як віртуальний вузол у погодженій структурі.

## Мінімальна модель

- `menu_nodes`: сайт, назва, URL, parent_id; для групувальних заголовків URL може бути відсутній.
- `articles`: один запис на нормалізований URL, статус обробки, контент і медіа.
- `article_menu_memberships`: article_id, menu_node_id, source_listing_url, page_number, component, first_seen_at.
- Унікальність articles за URL; унікальність membership за article_id + menu_node_id. Повторні спостереження за потреби зберігаються окремо.

Приклад результату для однієї статті:

```json
{
  "article_url": "https://www.americanrifleman.org/content/rifleman-review-taurus-raging-hunter-in-350-legend/",
  "navigation_paths": [
    ["Sections", "Reviews", "Guns"],
    ["Sections", "Reviews", "Gear"]
  ]
}
```

Приклад використовує Sections як віртуальну групу узгодженої карти. У перевірці Guns/Gear відкривалися через верхнє меню Reviews. Повний шлях визначається конфігурацією дерева, а source_listing_url — фактично відвіданою сторінкою.

## Алгоритм

```text
для кожного дозволеного menu_path:
    відкрити сторінку розділу
    для кожної сторінки через звичайний Next:
        отримати картки з обраних блоків
        для кожної картки:
            нормалізувати URL
            створити/знайти articles(URL)
            додати зв’язок article ↔ menu_path
            якщо матеріал ще не оброблений успішно:
                поставити його на завантаження та парсинг
        перейти через Next, якщо він доступний
```

Стаття, зустрінута повторно, отримує новий зв’язок із шляхом без повторного завантаження. Помилка попереднього завантаження не повинна назавжди блокувати повторну спробу. При паралельній роботі унікальність URL і постановка задачі мають забезпечуватись атомарно.

Контекст menu_path створюється до переходу у статтю і зберігається в черзі/базі, тому перехід на /content/... його не стирає. Парсер статті не мусить повторно виводити цей шлях із її HTML.

На кожному розділі зупинятися за видимою звичайною пагінацією. Якщо це 50 сторінок — збирати ці 50. Додати захист від повторення сторінки й відновлення проходу з checkpoint. Не встановлювати глобальну межу 50 для сайтів/розділів, що показують іншу кількість.

Playwright підходить для відкриття меню, підменю, пагінації та dynamic content. Завантаження самої статті можна залишити через наявний HTTP pipeline, передаючи збережений контекст. Це не змінює принципу збору зверху вниз.

Отриманий набір коректно описувати як «статті, доступні через обрані розділи і видиму пагінацію на дату збору». Це саме уточнений обсяг користувача; збір усієї історії сайту до нього не входить.
